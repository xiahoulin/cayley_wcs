## 2. 统一设计

### 2.1 设备点位约定与协议映射

引入“设备点位模板”，由 `设备类型 + 模板编码 + 版本` 标识，分别列出请求与响应点位。每个协议配置其支持的模板以及原生映射。同一个 HTTP 上位应用可以使用支持多个设备模板的 HTTP 协议；每条设备绑定选定一个模板及双方协议版本。

模板定义逻辑字段和业务约束，协议定义原生类型、地址与报文格式。匹配同一模板的逻辑字段，不比较不同协议的物理地址。例如 HTTP 的 JSON 键与 OPC UA 的 NodeId 不要求相同；它们映射到同一个 `cmd_TakeCoor_Row`。

建议持久化模板及版本、协议版本及点位映射、绑定的模板/双方版本/指纹；实体名称与迁移编号以实施时仓库实际状态为准。保留现有“一应用绑定一个协议”，在该协议下支持多个设备模板，避免一个 HTTP 应用只能连接一种设备。

点位维护信息：

| 信息 | 作用 |
|---|---|
| 逻辑字段编码、中文名称、说明 | 逻辑字段编码用于跨协议匹配，大小写敏感；名称用于显示 |
| 所属模板、方向、用途 | 方向=request/response；用途=对外业务点位/内部驱动点位 |
| 逻辑类型、协议原生类型 | 例如逻辑字符串与原生 TEXT/string；类型不能仅靠自由文本猜测 |
| 是否必填、是否允许空值、默认值 | 两端必须一致；默认值也要通过类型与范围校验 |
| 数值范围、枚举、数组元素/维度/长度、字符串长度/编码、单位、缩放 | 全部成为可校验的结构化信息；原有 value_range 自由文本保留作说明 |
| 原生地址、rw、排序 | NodeId、寄存器/字节序、主题或帧位置等由协议编辑器显示 |

对外业务点位在所选模板内必须完整匹配，额外字段、缺失字段、重复字段、错误方向均禁止建立关系。内部点位也可维护并校验，但不强迫上位应用填心跳、复位、任务确认等控制信号。内部驱动必需点由设备处理器声明，发布与建连时检查；上位传入这些控制字段按未知/禁用字段拒绝。

点位身份由“协议版本 + 模板版本 + 操作 + 方向 + 逻辑字段编码”确定，并设数据库唯一约束。同一字段可用于不同设备模板或请求/响应，但匹配和读写必须带齐上下文。ManagedConnection 只加载当前设备选定模板与协议版本的映射，以操作/方向/字段建立索引；重复定义直接拒绝，禁止沿用按字段名取第一项的做法。处理器发出的逻辑操作先解析到确定的原生点位，再执行 I/O。

值约束分三层：对外请求的业务取值要求、协议原生类型能够表达的物理值域、内部驱动在当前阶段允许的操作和值。例如坐标在实际取放货时必须有效，但完成清理时驱动允许写零；清零只经过原生类型和驱动阶段校验，不能因此放宽外部请求。各 taskType 所需坐标及未使用坐标的零值规则在模板中明确条件约束。处理器必需点还声明 R/W 能力；cmd_TaskNum 需要回读时必须实际支持读，不能保留 W 配置后绕过权限。

### 2.2 方向的唯一解释

- 请求：上位应用 → WCS → 设备的业务命令点位。
- 响应：设备 → WCS → 上位应用的结果、状态点位。响应可能来自异步轮询或消息，不等同于一次 HTTP 请求立即执行完成。
- `rw` 是 WCS 对物理点位的访问权限，独立于上述方向。命令点允许为回读配置 RW，响应点的实际可写权限不会自动转为上位写权限。
- HTTP 返回“受理成功”是任务元数据；设备执行结果要按任务查询、快照或回调读取。
- 既有 From_WCS/To_WCS 可辅助迁移方向，不能仅凭 R/W 自动决定业务用途；无法确定的点位进入待确认草稿，不静默启用。

### 2.3 两两类型匹配与严格值校验

采用统一逻辑类型注册表，再定义各协议的原生类型映射和编码能力，生成两两匹配结果。这样 TEXT 与 string 可以匹配，也避免维护多套相互矛盾的判断。

| 情况 | 规则 |
|---|---|
| TEXT、STRING、string | 归一为 STRING；仍核对长度、编码、空值规则 |
| BOOL、BOOLEAN、boolean | 归一为 BOOL；不把任意字符串/任意非零数静默变成布尔值 |
| INT、UINT、WORD、DINT、DWORD 等 | 先按协议上下文明确位宽、符号及用途；WORD 不自动视为有符号 INT |
| HTTP integer/number | 必须由点位模板指定整数范围/精度，不能据 JSON number 推断为任意 PLC 数值类型 |
| 不同原生宽度 | 仅在双方逻辑类型、完整允许值域相同且转换无损时匹配；不只检验本次样例值 |
| 浮点与整数、布尔与整数、字符串与整数 | 默认不自动相互转换；显式 wire 编码与逻辑类型分开，禁止隐式业务类型转换 |
| REAL/LREAL/FLOAT/DOUBLE | 根据协议明确实际精度；精度不一致不自动放行，拒绝非有限值 |
| ARRAY | 元素类型、维度、固定/最大长度、顺序一致；不再把标量包装成数组或把数组全部转 Long |
| 超出 JSON 安全整数的 64 位数 | 模板明确十进制字符串的无损 wire 编码，前后端及适配器一致执行；不能先经过 JS Number |
| scale/单位/枚举 | 逻辑语义相同，原生缩放经可逆转换校验；枚举完整一致，不只比较几个常用值 |
| 未知类型或设备不支持的复合结构 | 发布失败，给出明确字段与原因，不回退成字符串 |

当前注册的适配器为 8 种：`http`、`opcua`、`modbus_tcp`、`s7`、`mqtt`、`tcp`、`sim`、`loopback`；前 6 种为外部协议，后 2 种为测试适配器。实施时生成 **8×8 共 64 个有方向的类型匹配组合**，请求和响应分别测试，包括同协议组合；新增 provider 未登记能力时默认拒绝。

这里的 64 组合指字段/类型/编解码匹配，不代表系统自动具备 64 种网络网关服务。当前 `/open/**` 是 HTTP 入站；其余适配器是 WCS 对设备的连接端。应用关系同时校验实际角色与操作能力，类型通过但没有可执行的收发入口，不能显示为“可连接”。本次完善现有六类外部适配器的发送和解析，不凭类型矩阵宣称新增了 OPC UA/S7/Modbus 入站服务器等未实现角色。

### 2.4 HTTP payload 结构

正式拼写统一为 `payload`。业务点位使用模板中统一的逻辑字段编码。堆垛机示意如下（仅说明拟定结构，正式文档示例由实施后的数据验证生成）：

```json
{
  "app_id": "调用方应用标识",
  "app_key": "调用方应用公钥",
  "access_token": "令牌",
  "request_id": "本次请求编号",
  "data": {
    "appId": 123,
    "taskNo": "WA1001",
    "priority": 5,
    "wmsRef": "IN-2025-001",
    "payload": {
      "cmd_TaskType": 1,
      "cmd_TakeCoor_Row": 1,
      "cmd_TakeCoor_Column": 2,
      "cmd_TakeCoor_Floor": 3,
      "cmd_PutCoor_Row": 1,
      "cmd_PutCoor_Column": 4,
      "cmd_PutCoor_Floor": 5,
      "cmd_PortNum": 1
    }
  }
}
```

处理规则：

1. 凭证、目标设备 appId、业务任务号、优先级、业务引用等保留为公共字段；设备任务类型和取放坐标等全部进入 payload。此处 appId 是目标设备数据库编号，与外层调用方 app_id 分开。
2. 模板版本从已发布的绑定确定，调用方不能在 payload 中更改设备类型、地址或绕过授权。入队保存模板版本及请求快照。
3. 调整单任务、每个任务链段、管理端手工建任务、设备处理器、持久化、查询及回调投影。任务链公共业务附加信息不能自动混入设备点位；每段独立 payload，不做隐式继承。
4. 任务查询中的 `payload` 保留原始请求点位；执行结果用 `result: {capturedAt, quality, payload}` 表示响应点位。设备快照在连接信息的 payload 中返回响应点位。回调保留事件、编号、状态等公共字段，携带与任务查询一致的 result 对象。
5. 未采集到有效结果时 result 为 null；读失败、缺字段、过期数据不得伪装成零值或正常结果。实时快照可返回坏质量及具体错误，但不据此推进状态机；最终任务结果必须来自本任务执行时的有效采样，不能拿后来另一任务的设备状态冒充。
6. 获取 token、管理端登录/点位配置/授权等不是设备点位报文，沿用其专用结构。HTTP 业务设备读写统一 POST JSON；外发 HttpAdapter 同样把业务点位放在 payload，解析对端响应 payload。
7. 控制协议需要的 cmd_TaskNum、cmd_ConfirmTask、WCS_Heart 等由 WCS 内部驱动产生；上位不能透传这些字段启动/确认设备。业务 taskNo 原样保留，由 WCS 持久化分配另一个原生设备任务号，详细规则见第 4 节，禁止将异常转换为 0。
8. 管理端真实设备点位 I/O 也纳入统一结构：`/connection/write` 使用 `{appId, payload:{点位编码:值}}`，返回写回执及 payload；`/connection/read` 使用 `{appId, payload:{点位编码:null}}` 选择待读字段，null 仅为 read 操作的选择标记，绝不当作写值，响应在 payload 中返回值及独立质量元数据。同步 ConnectionView、API client 和联调脚本。仍使用管理端 JWT；内部控制点写入必须走已授权的受控运维操作与设备级互斥，在任务占有设备时不得用任意单点写干扰握手。

最终任务结果在设备完成反馈时、发送完成确认/清零之前采集并校验，与“准备完成确认”的持久化步骤一起保存。有原生任务号反馈的设备须匹配本任务编号；自动门等无该反馈点的设备，以设备级单飞、持久化执行代次、本次命令后的新鲜反馈及对应处理器状态规则确认归属，不能强行添加不存在的设备点位。内部执行代次不等于设备端精确去重；写入超时、重启后执行情况不明时，只允许设备处理器已声明的幂等目标状态恢复（例如自动门目标开/关状态），其他无法确认的动作挂起核实，禁止盲目重放。随后发生重启时复用已保存结果并按握手状态恢复，不能事后从 latest 抄取零值或下一任务的状态。查询和回调使用该持久化结果。

“对外字段完整匹配”针对选定设备模板和方向，不要求一个查询请求携带派工点位，也不把 WCS 内部握手字段加入上位必填项。

已有设备的请求映射在本次一并确定，避免只收敛堆垛机：

| 设备类型 | 旧参数 | 新 payload 业务点位 |
|---|---|---|
| stacker / palletizer | taskType、takeRow/takeColumn/takeFloor、putRow/putColumn/putFloor、portNum | cmd_TaskType、cmd_TakeCoor_*、cmd_PutCoor_*、cmd_PortNum，见上例 |
| conveyor | payload.toStation | payload.cmd_DestStation |
| lift | payload.targetFloor | payload.cmd_TargetFloor |
| auto_door | payload.action=open/close | payload.cmd_Open 与 payload.cmd_Close；都是 0/1 整数，两个必填且恰好一个为 1 |

自动门的开/关字段是业务动作选择，两个值及“恰好一个为 1”在入队前完成校验；入队后仍由门处理器检查运行模式、故障和占位成功，再按“先清对向命令为 0，写回执成功后再发目标动作 1”的顺序执行并在完成后清零，不由 HTTP 直接转发到设备，不按 Map 遍历顺序写入。现有 action 的 open/close 仅用于受控历史迁移；未知值不得默认开门。请求/响应模板两端都采用对应新字段和同一逻辑类型，不能以“字符串 action 可隐式转布尔命令”绕过严格匹配。

迁移保留不含认证凭据的原始业务请求快照及转换记录。历史 fromStation 等没有对应物理点位、仅作业务记录的内容保存在历史/公共业务附加信息中，不静默丢弃，也不冒充设备点位加入新 payload；新入参中的设备点位必须在所选模板内有明确定义。

### 2.5 各协议点位对象与收发

| 协议 | 拟实现/修正 |
|---|---|
| HTTP | POST JSON 的请求/响应 payload；校验状态码、响应结构和点位值；健康探测与业务操作分开，不把 token 流程改成点位接口 |
| OPC UA | 逻辑点位映射 NodeId、原生数据类型及读写权限；按原生 Variant 类型编码，校验读写状态码、数组和节点类型，保留堆垛机握手顺序 |
| Modbus TCP | 逻辑点位映射线圈/寄存器、地址、位宽、符号、字节/字序、缩放；多寄存器一致读写，失败不回报成功 |
| S7 | 逻辑点位映射 DB 地址、位偏移、原生类型、长度、字节序；检查 PLC4X 返回码及完整读写结果 |
| MQTT | 按显式消息格式选择点位对象 JSON 或明确的单点 wire 编码；请求/响应主题、关联编号、重发去重和超时；不将 Map.toString 当 JSON，不将陈旧 retained 状态误认成新任务响应 |
| TCP | 实现明确版本的长度前缀 JSON 点位帧（字段规范、字节序、长度上限、关联编号）作为可用默认格式；处理粘包、拆包、超时、并发响应、断线。任意厂商私有二进制协议需具体帧配置/codec，不能宣称自动适配 |
| sim / loopback | 执行同一模板与类型校验，用于逻辑回归；它们通过不能代替上述真实网络协议验证 |

共享 `PointMessage` 包含版本、操作、关联信息、方向及点位值；适配器再转换为各自的协议点位对象与原生报文。PLC 协议无需在网络上发送 JSON payload，HTTP/MQTT/TCP 也不能直接转发 Java Map 字符串。

对于一次业务命令多个点位：全部值先校验，再按驱动顺序写参数，最后写提交/执行信号；中途写失败不发执行信号。读写回执逐点检查，不能只等待 future 完成。轮询返回数据质量和采集时间，不能吞掉异常后将残缺快照当作正常响应。

## 3. 绑定、版本和维护界面

### 3.1 统一匹配流程

依次校验：应用有效性及固定归属 → 协议/模板已发布 → 设备处理器与收发角色支持 → 请求字段集合与方向 → 响应字段集合与方向 → 原生类型可无损映射 → 必填/范围/枚举/单位等约束 → 内部驱动必需点位 → 形成双方版本指纹。

前端显示逐字段差异：缺少/多出字段、类型不兼容、方向错误、数组长度/枚举/取值域不同、原生映射缺失、无对应收发能力。一个上位批量授权多个设备时，全部验证通过才在同一事务保存；失败不改变原授权。

共用服务覆盖：create/update/grant、软删除关系恢复、启用关系、应用换协议/换设备类型、连接打开/重连/恢复、任务入队及链段实际选机。查询授权保留原有校验；失配后的新指令禁止发送，不因缓存旧绑定放行。

独立任务和链任务都从已认证上下文保存可信调用方、绑定标识/版本、固定归属、模板/协议版本；这些信息不接受客户端自报。管理派工记录真实运维身份与专用授权来源。在首次参数写入及发送执行确认之前（含重试）复验应用有效/启用、关系授权、版本和设备当前配置。失效的未启动任务挂起并说明原因，零新设备命令；已经被设备受理的任务由内部驱动按原版本继续必要的完成确认、清理和结果留存。token 过期或撤销上位授权不等于取消物理作业，也不能阻止在飞任务安全收尾。

幂等命中必须先核对可信调用方及授权，不能将另一上位应用的同名任务/链当作本调用者的重试返回。历史任务缺乏可信来源时列为待核对，不自动赋予系统授权；已有任务的必要收尾依旧遵守原设备归属和持久化执行状态。

链的 candidateAppIds 全部属于同一模板版本/允许值域并具备授权才可接收；选机物化时复验绑定版本、授权和点位能力，不能仅校验候选中的第一台。

### 3.2 编辑、发布与运行中变更

- 点位界面支持新增、编辑、删除、复制、排序、请求/响应筛选与内部/对外筛选；按协议展示地址编辑器和原生类型选项。应用页展示所选协议及模板，绑定页显示可连接/不匹配原因。
- 草稿可改；已发布版本不可原地改类型、方向或地址，修改生成新草稿版本。草稿乐观锁，数据库对版本内字段唯一性兜底。
- 发布新版本不会立即替换在用连接。激活前检查相关设备的所有非终态任务及未完成链候选引用；有依赖时拒绝切换并显示清单，不能自动取消任务或复位设备。FAILED 也可能对应尚未停止的物理任务，因此还须通过旧连接确认设备空闲、没有待确认/未清理任务、没有 I/O 或重试占位；设备离线或状态无法确认时拒绝激活。
- 任务、链段持久化选用版本，重试和进程重启继续使用原版本；所有 retryTask/resetForRetry、自动恢复和链重试再次检查原版本与当前连接配置。失配时挂起并提示“恢复原版本或按受控流程转换”，不在新地址上重放旧 payload。版本切换锁定应用/绑定相关记录并复验，防止“检查通过后又被修改”。
- 切换采用设备级调度/I/O 栅栏与持久化配置代次：先停止新调度并等当前 I/O 安全结束；进入切换中状态后更新所选版本，关闭旧连接并新建连接，验证通过再恢复派工。连接建立、轮询、看门狗、恢复器、任务 worker、运维写入都携带并检查配置代次。旧连接晚到、旧采样晚到、旧 worker 命令不得重新挂回 RUNNING 或继续写入。
- 切换失败或进程中断保持禁止派工，重启只按持久化选定版本恢复；不会同时启用新旧连接。刷新 ManagedConnection 点位索引及其他缓存，重连不能再次装载旧版本。为单设备配置固定锁顺序，避免激活、下发、取消、恢复互相死锁。
- 点位/协议删除不得产生悬空引用；在用已发布版本只能退役，仍保留历史查询。后台校验有效归属，前端不新增租户输入项。

## 4. 迁移与 WMS 联动

1. 先对当前数据库做只读盘点并保存不含凭据的基线：协议、点位、应用、绑定、活动任务/链、现有 payload 与平铺字段差异。新增版本化 Flyway，不修改已执行迁移。
2. 为已实现的 stacker/palletizer/conveyor/lift/auto_door 整理模板及协议映射；保留现有设备处理器。字典预留而没有处理器的设备不能因此变成可执行设备。
3. 已知种子按明确映射生成草稿及迁移记录；原生类型/范围冲突、缺失点位或客户自定义含义不明时列出逐项差异。必须解决才能启用，不能将全部老绑定一律认定兼容。
4. 先新增结构，保留旧列作为历史/回退依据。将旧堆垛机 task_type、坐标、端口映射为统一 payload；已有 payload 与平铺值冲突时阻止自动迁移并报清单。任务链段、待重试任务和历史记录分别处理；在飞任务完成前不换协议。迁移不得通过改 last_update_time 触发重复库存记账/终态回调。
5. **由 WCS 统一分配原生设备任务号**：针对具有原生任务号点位的设备，业务 taskNo 保持原值，新增持久化 native_task_num；单任务、管理派工及链子任务全部走同一分配器，链号中的数字和段号不再拼接成 PLC 任务号。分配在目标设备已确定、即将开始派工时进行，合法范围取自已发布协议的真实原生类型与设备程序保留值，不统一写死 65534。设备级分配记录加事务锁及活动号码唯一约束，先保存对应关系再写设备，重启和重试复用同一映射。任务完成握手且反馈确认清理后才释放活动占用；故障/通信超时不立即释放，也不让新任务接管旧号码。回绕复用前核验设备空闲、上一任务按协议完成确认以及采样新鲜性；部分设备保留 status_TaskNum，因此不普遍要求反馈数字归零。无原生任务号的设备按第 2.4 节关联任务与响应。旧在飞任务保留旧版本及原数字映射，超出新值域也不擅自重新编号，必须排空或受控处置。WMS 可保留既有业务 taskNo 格式，但不再承担 PLC 数字范围约束；文档删除调用者必须自行生成 PLC 数字号的要求。
6. WMS 修改 `CayleyWcsAdapter` 将现有业务字段转换到上面所示 payload，查询/回调解析同步适配；保留既有 token 缓存、明确鉴权拒绝后重取一次、目标设备授权和业务终态去重。WMS 内部仓库坐标模型无需为公共协议结构强行删除。
7. 切换采用 WMS/WCS 协调发布：停止新任务下发并排空受影响设备/链，备份当前数据与镜像；验证迁移和绑定后启用新接口。新接口只接受 payload 点位格式；旧字段出现在新请求时明确报错，不建立长期双入口。正式切换前的版本协商/开关需由服务端验证，不能靠客户端随意开关绕过。
8. 同 appId + taskNo（链按其既有业务键）重试：在可信调用方一致且当前允许查询/重试的前提下，保存规范化请求指纹，同内容返回同任务，不同内容明确冲突；唯一约束解决并发重复创建，另一调用方碰撞只返回不含原任务详情的冲突。历史请求先按其固定版本转换比较，不因格式迁移额外派工。新增唯一约束前盘点历史重复键并做明确处置，不删除历史执行证据。任务号幂等、PLC 数字号租用和 access_token 重试分开测试。
9. 回退须成套恢复兼容的 WMS/WCS 镜像及配置；增量迁移保留旧列。若新版本已产生无法由旧版解释的新任务，先排空并导出转换验证，不直接回退旧代码处理新数据；不删除既有测试数据。
