任务 `TASK-20261112-52D24ADC`，时间为 Asia/Tokyo。私有发布资料位于 `%LOCALAPPDATA%/CayleyWCS/deploy/20261112-jvm-c2-fix/`。配置、转储、实车数据及系统事件原文不进入版本库。

## 已确认的故障位置

原 Temurin 25.0.4.1+1 在启动后 25.258 秒发生 SIGSEGV，退出码 139，未发生容器 OOM。崩溃线程为 `C2 CompilerThread1`，正在第 4 层编译 MyBatis 3.5.19 的 `DynamicContext$ContextMap.get`（63 字节）。原生栈为 `IfNode::Ideal_common` → `RangeCheckNode::Ideal` → `PhaseIterGVN::optimize` → `Compile::Optimize`，故障地址为 `0x10`，寄存器 RDX 为零。这确定了 HotSpot 优化编译阶段的原生空指针访问位置；Java 业务异常和 OPC UA 证书日志不能解释这个原生崩溃。

原运行 Dockerfile 使用浮动标签 `eclipse-temurin:25-jre`，本机缓存仍为 25.0.4.1+1。它没有提供可复现的 JVM 版本保证。当前修正为 Temurin 25.0.5+8，并固定官方镜像摘要：

```text
eclipse-temurin:25.0.5_8-jre@sha256:ecdc0adb37bde1a281c4d245a3cd535004b1fc8322d560f5b09463b248c81df0
```

Temurin 25.0.5+8 的发布见 [Adoptium 公告](https://adoptium.net/news/2026/10/eclipse-temurin-17021-21013-2505-2701-available)，原始变更见 [OpenJDK 25u 版本对比](https://github.com/openjdk/jdk25u/compare/jdk-25.0.4.1%2B1...jdk-25.0.5%2B8)。其中含多项 C2 修改；原崩溃函数本身在这两个标签中一致，不能仅凭版本更新或相似标题把某一补丁认定为本次事故的唯一修复。

## 归因边界

新旧 JVM 的最小探针均通过，旧版完整 WCS 的首次隔离对照也成功完成目标方法的 C2 编译，未复现原 SIGSEGV。后续旧版实验在 65.273 秒触发另一处 C2 内部断言：`PhaseOutput::fill_buffer` / `output.cpp:1816` 的代码块尺寸保证失败，编译目标为 `java.util.regex.Matcher.replaceAll`。该次配置尚未连通 SEER 模拟器，不能将失败归因于 AGV 报文。崩溃日志和 2.2 MiB 编译回放数据均已保存；后续连通 SEER 模拟器的旧版运行 120 秒未崩溃。

补齐 Spring Boot Loader 类路径后，同版 25.0.4.1 的回放无解析错误、目标方法完成第 4 层编译且退出 0，没有复现断言。新版也完成目标方法编译，但报告两处 JVM 类常量池不匹配，因此不将跨补丁版回放视作严格对照。新旧 JVM 另各跑 6 个编译顺序扰动种子，12 组参数读取及动态 SQL 校验均正确。

当前证据能定位故障组件及崩溃机制，尚不能确定触发条件或唯一上游缺陷编号；升级后的稳定运行是整改验收证据，不是严格的旧版失败、新版通过的根因证明。**运行时整改已验收，唯一根因追踪仍保持未完成。**

宿主机系统事件另有已更正的处理器硬件错误：11 月 9 日事件 19 明确记录处理器核心 TLB 错误，APIC ID 25；11 月 12 日 14:28 的事件 2 包含处理器错误节。用户确认没有调整过 CPU 超频、降压或内存 XMP，不能将问题归因于手动调参。这些系统事件与 17:25 的 JVM 崩溃没有相同时间证据，不能据此宣称 CPU 损坏或认定硬件就是根因。WHEA 对“已更正错误”的含义见 [Microsoft 定义](https://learn.microsoft.com/en-us/windows-hardware/drivers/whea/hardware-errors-and-error-sources)。未修改宿主机 BIOS、微码、电源或硬件设置。
